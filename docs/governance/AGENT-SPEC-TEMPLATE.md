## 4. 工作流

### 4.1 执行顺序

沿用 `docs/ai/agent-rules.md` 第 9 节的模块实现顺序，此处定义该代理的执行阶段：

| 阶段    | 动作                             | 产出                 | 验证             |
| ------- | -------------------------------- | -------------------- | ---------------- |
| 1. 准备 | 阅读 SPEC.md 全文，确认 FR/BR/AC | 理解确认             | -                |
| 2. 骨架 | 创建目录结构和 go.mod            | 可编译的空骨架       | `go build ./...` |
| 3. 接口 | 定义接口和错误变量               | 接口文件 + errors.go | 编译通过         |
| 4. 实现 | 逐个 FR 实现核心逻辑             | 功能代码             | 单元测试通过     |
| 5. 测试 | 为每个 FR 编写测试               | 测试代码             | `go test -race`  |
| 6. 自查 | 对照 spec 验收标准自查           | 自查报告             | AC 全部通过      |
| 7. 报告 | 输出变更报告                     | 变更报告             | -                |

### 4.2 输出格式

每次执行完成后，必须输出：

```markdown
## 变更报告

### 修改文件清单
- {文件路径}: {变更说明}

### 覆盖的 Requirements
| Requirement | Status | Evidence |
|---|---|---|
| FR-001 | ✅ | TestXxx_TC001 |
| FR-002 | ✅ | TestXxx_TC002 |

### 测试说明
- 新增测试：{数量}
- 测试命令：`go test ./{module}/... -race -count=1`

### 验证方法
{如何验证变更正确}

### 风险
{可能的破坏性影响}
```text

## 5. 质量标准

### 5.1 代码质量

| 指标   | 标准              | 验证方式                  |
| ------ | ----------------- | ------------------------- |
| 编译   | 零错误零警告      | `go build ./...`          |
| 测试   | 全部通过 + 无竞态 | `go test -race`           |
| 覆盖率 | ≥ 80%             | `go tool cover`           |
| Vet    | 零警告            | `go vet ./...`            |
| Lint   | 零警告            | `golangci-lint run`       |
| 依赖   | 无未批准依赖      | `go mod tidy && git diff` |
| 安全   | 无硬编码 secret   | `gitleaks detect`         |

### 5.2 Spec 合规

| 检查项             | 标准                                 |
| ------------------ | ------------------------------------ |
| FR 覆盖            | spec 中所有 FR 均有实现              |
| AC 验证            | spec 中所有 AC 均通过                |
| TC 存在            | spec 中所有 TC 均有对应测试          |
| Edge Cases         | spec Section 13 的边界场景均有测试   |
| Error Handling     | spec Section 12 的错误均有处理       |
| Performance Budget | spec Section 17 的指标均达标         |
| Non-goals          | 未实现 spec Section 4 列出的禁止功能 |

### 5.3 输出质量

| 检查项           | 标准                         |
| ---------------- | ---------------------------- |
| 文件清单         | 列出所有新增/修改/删除的文件 |
| 变更说明         | 每个文件说明改了什么、为什么 |
| Requirement 覆盖 | 对应 FR/BR 编号              |
| 测试说明         | 新增/更新了哪些测试          |
| 验证方法         | 可执行的验证命令             |
| 风险评估         | 可能的破坏性影响             |

| ------------- | ------------ | ------------------ |

| code-reviewer | 接收代码审查 | 代码变更后         |
| {其他代理}    | {协作方式}   | {触发条件}         |

### 6.2 上下文传递

当代理交接时，必须传递：

- 当前阶段（参照第 4.1 节执行顺序）
- 已完成的 FR 列表
- 未完成的 FR 列表
- 遇到的阻塞问题
- 当前修改的文件清单

### 6.3 失败处理

| 失败类型   | 处理方式                     |
| ---------- | ---------------------------- |
| 编译失败   | 立即修复，不进入下一阶段     |
| 测试失败   | 分析原因，修复实现（非测试） |
| AC 不通过  | 回溯到实现阶段重新修改       |
| 依赖缺失   | 停止执行，请求人工批准       |
| spec 冲突  | 停止执行，请求 spec 澄清     |

## 7. 记忆策略

### 7.1 短期记忆（单次执行内）

- 当前正在实现的 FR 编号
- 已修改的文件列表
- 已编写的测试列表
- 遇到的错误和解决方案

### 7.2 长期记忆（跨执行）

- 模块的接口变更历史
- 常见错误模式和修复方法
- 性能优化经验
- 依赖模块的接口约定

### 7.3 上下文窗口管理

当上下文窗口接近限制时：

1. 优先保留：当前 SPEC.md、agent-rules.md、当前 FR 的代码
2. 可丢弃：已完成 FR 的详细代码（保留摘要）
3. 可延迟：测试输出、lint 输出（按需重新获取）

## 8. 特殊场景

### 8.1 Spec 不完整

如果发现 spec 不完整或有歧义：

1. 记录到 spec 的 Open Questions（Section 23）
2. 标记为 Blocking 或 Non-blocking
3. 如果是 Blocking，停止执行并请求澄清
4. 如果是 Non-blocking，记录假设并继续

### 8.2 Breaking Change

如果实现过程中发现需要 Breaking Change：

1. 停止当前实现
2. 记录 Breaking Change 的范围和影响
3. 请求人工审批
4. 获得批准后，更新 spec 并重新走 Review

### 8.3 性能不达标

如果实现后 Performance Budget 不达标：

1. 记录当前性能数据
2. 分析瓶颈（profiling）
3. 尝试优化（不改变接口）
4. 如果仍不达标，记录到 spec 的 Open Questions
