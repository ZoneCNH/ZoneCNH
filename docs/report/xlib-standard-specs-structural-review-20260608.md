## 1. 结构性问题清单（按严重度）

### S1【严重】多权威源并存，单一事实源（SSOT）失效

**现象**：

- `SPEC.md`（1,496 行）和 `MODULE-SPEC.md`（448 行）覆盖几乎相同的章节（模块身份、分层模型、API、Harness、Evidence、L2 ladder、DONE 模板……），README 声称后者独有内容"已合并"，但 448 行实际并未删除或折叠。
- `DEEP-ANALYSIS.md`（536 行，181 文件历史口径）同样未删除，仍出现在工件清单。
- 三者均有自己的 Status 字段（`Draft` / `consolidated` / 历史），无统一生命周期标记。

**后果**：

- 任何条款变更必须三处对照，维护成本 ×3，且 README 的免责声明无法被工具强制。
- 下游或代理读取时，无法从目录结构推断"读哪一个就够了"。

**影响维度**：SSOT、维护成本、一致性

---

### S2【严重】多套口径并行，靠免责声明而非合并解决

| 项目       | SPEC.md 当前口径             | DEEP-ANALYSIS.md 历史口径      | 其他出现位置                          |
| ---------- | ---------------------------- | ------------------------------ | ------------------------------------- |
| 输入文件数 | 154                          | 181                            | COVERAGE-MANIFEST = 154，CONFLICT §16 |
| 规则总数   | 419（active 363/87%）        | 419                            | —                                     |
| Gate 总数  | 66                           | 66（早期 "17+/20+" 已 retire） | CONFLICT §17                          |
| ADR 数量   | 9 正式 + 1 template + 3 历史 | "13 个文件"                    | CONFLICT §18                          |
| L2 适配器  | 7（计划文件 15）             | —                              | §22.1 注释                            |
| PR 执行包  | 28（自身）+ 20（下游同步）   | 28                             | §6.7 / §6.8                           |

**问题**：README + 多个章节用"历史口径不得覆盖当前主规格"作脚注消化冲突，而不是把过期数字物理删除或归档到独立 `archive/` 子目录。读者必须先解析"哪个数字是当前权威"才能继续。

**影响维度**：一致性、可读性

---

### S3【严重】FR 条款互相循环引用，主定义分散

- `FR-003 → FR-047`（Git 治理引用 5 层执行链权威定义）
- `FR-006 → FR-050/FR-051`（采纳状态机入口约束引用枚举/转换权威定义）
- `FR-050` 又反向声明"FR-006 引用的权威定义"
- 7 条 Iron Rules（§7.1）与 15 条 TRUTH（§22.4）语义重叠：IR-001 ≡ TRUTH-008（"没有证据不允许 DONE"）、IR-007 ≡ TRUTH-15（"登记态 ≠ adopted"）、IR-005 ≡ TRUTH-12 等。
- 8 个采纳状态、6 个禁止转换：分散在 §7.5、§9.7、FR-050、FR-051 共 4 处。

**后果**：单一规则的权威定义需要跨 3–4 个章节拼接，自动化提取（rule-id → schema）困难。

**影响维度**：可机读性、一致性

---

### S4【高】"非可执行索引"与"FR + WHEN/THEN 合约"角色混用

- SPEC.md §0–§2 明确：本规格只能证明"本地输入文件已被整理成规格包"，不能证明远端、发布、下游。
- 同一文档 §6 又承载 52 个 FR + 104 条 WHEN/THEN，措辞是机器门禁式硬约束（`returns non-zero exit code`、`gate fails`、`阻断发布`）。

**矛盾**：下游消费者无法判断这些 FR 是"读者用的描述性索引"还是"goalcli/enforcer 必须实现的合约"。如果是前者，WHEN/THEN 形式过重；如果是后者，免责声明就削弱了它们的强制力。

**影响维度**：边界清晰度、可执行性

---

### S5【高】追溯表是章节级而非 rule 级，且不可机器消费

`TRACEABILITY.md` 仅 62 行、约 25 条映射，全部是"模块身份 → docs/spec.md, docs/standard/xlib-standard.md, docs/standard/repository-roles.md"这种文件级锚点：

- 无 rule-id（419 条 RULE-\*）到 file:line 的映射
- 无 commit/tree-sha
- 路径是本机绝对路径 `<upstream-root>/...`
- 同一文档自述："本表只证明主要条款有来源锚点，不是逐规则证明账本"

**与 SPEC.md 自我目标矛盾**：FR-001 要求"419 条规则全部机器化为 registry.yaml"，TRUTH-04 要求 "Proof 是完成的唯一合法证明"，但本目录的追溯证据本身就达不到机器化、可证明的标准。

**影响维度**：可追溯性、可机读性

---

### S6【高】覆盖清单依赖本机绝对路径，跨环境不可复现

`COVERAGE-MANIFEST.md` 罗列 154 条 `<upstream-root>/...` 和 `<external-downloads>/...` 路径，自承"不是可移植 source bundle"、"若迁移到其他机器必须重新生成"。

- 缺：commit sha、tree sha、文件级 sha256
- 缺：相对路径或仓库根锚点
- 上游仓库一旦 rebase/move/rename，本清单立即过期且无法 diff 检测

**与 SPEC.md FR-027 矛盾**：FR-027 要求 release manifest 含 `source_digest`、`tree_sha`，本目录自己的"覆盖证明"却没有。

**影响维度**：可追溯性、可移植性、维护成本

## 3. 优先级建议

### P0（影响 SSOT，必须先做）

1. **物理废止 MODULE-SPEC.md 与 DEEP-ANALYSIS.md**：移动到 `specs/xlib-standard/archive/` 或彻底删除，README 中只保留 4 个当前工件（SPEC / TRACEABILITY / CONFLICT-LEDGER / COVERAGE-MANIFEST）。如保留，必须明确"非规格、仅历史"且在仓库 lint 检查中排除。
2. **声明本目录与上游 `github.com/ZoneCNH/xlib-standard` 的关系**：是 snapshot 还是 fork？在 README 顶部记录 `Upstream: <repo>@<commit>` 锚点。

### P1（影响可追溯性 / 可机读性）

1. **覆盖清单加 digest**：每个输入文件增加 `sha256` 与相对路径（相对 upstream 仓库根），删除 `<upstream-root>/` 前缀。
2. **追溯表升级为 rule 级**：从 419 条 RULE-\* / 52 个 FR 各取唯一 ID，映射到 `file:line` 或 `file#anchor`，生成 `traceability.yaml`。
3. **抽取机器可读 schema**：419 规则 / 66 gate / 8 状态 / 9 ErrorKind / 15 TRUTH 生成 `registry/*.yaml`，Markdown 表格改为从 yaml 渲染。

### P2（影响可读性 / 维护成本）

1. **拆分 SPEC.md**：按主题切到 `spec/00-metadata.md`、`spec/01-functional-requirements.md`、`spec/02-contracts.md`……目录化；保留 SPEC.md 作目录入口。
2. **消除 Iron Rules / TRUTH 重复**：合并为单一 `truths.yaml`，按编号分类，Markdown 只渲染。
3. **CONFLICT-LEDGER 与 SPEC 章节互引**：每条取舍加 `Resolved in: SPEC §X.Y` 字段，SPEC 端反向加 `See: CONFLICT-LEDGER §N`。

### P3（清理项）

1. **§22.1 关键数字表自动生成**：从 schema 渲染，禁止与正文出现差异。
2. **§23 最终验证**：替换为 CI 跑出的 checklist artifact，不再是文档内手填 checkbox。

## 4. 风险与背书

- 本评分基于本仓库本地工件静态分析。未访问上游 `github.com/ZoneCNH/xlib-standard` 源仓库，因此 S9 的"与上游边界"判断可能因上游已有同步规则而下调严重度。
- 154 个输入文件未抽样核对内容；本报告假定 COVERAGE-MANIFEST 中文件存在性、内容由原作者保证。
- 评分权重为分析者主观选择；如优先发布、可读性高于机器化，未加权平均分（4.0）也可作为参考下限。
