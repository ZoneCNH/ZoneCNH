我看完 `docs/goal` 后的判断是：

**这个目录不是“缺架构”，而是已经出现了“治理层架构熵增”。**
它的目标很清楚：用 Goal、Spec、Matrix、Gate、Evidence、Agent 协议形成一个 Goal Delivery OS。但现在的问题是，同一套规则被写在太多地方：文档、模板、`.config/goal`、Registry、CI、脚本、Gate、Agent Protocol 都在描述同一批概念，导致它自己也开始产生“半权威”。仓库里的 `24-standard-unification-analysis.md` 已经直接指出：当前不是缺少标准，而是多个标准面并存，结构统一分数只有 66/100，ID、schema、状态枚举、Matrix、Evidence、Gate 语义都还没完全统一。([GitHub][1])

## 结论

`docs/goal` 的熵减方向不是继续加文档，而是：

> **把 Goal 体系从“文档驱动”改成“Schema 编译驱动”。**
> Schema 是权威；文档、模板、脚本、CI、Agent Context 都是投影。
> 投影不一致，就算失败。

也就是说，不要再让 AI 去读二十多个 goal 文档后“理解规则”。应该让 AI 读一个很短的 canonical model，再由 schema、lint、gate、CI 保证它不能偏离。

---

## 它已经做对了什么

`00-authority-map.md` 已经在试图区分“哪里是权威，哪里是投影”，并且规定 README、SOP、Runtime、CI、schema、examples 只能引用、校验或投影 SSOT，不能私自定义新的状态、Gate、ID、Registry、Matrix、Evidence 规则。这个方向是对的。([GitHub][2])

`03-pipeline.md` 也把主流程定义成 11 层：Goal → Spec → Design → Plan → Tasks → Prompt → Code → Test → Review → Release → Retrospective，并且明确 Matrix 是横切追踪工件，不是主流程阶段。这个设计可以防止 Matrix 变成又一个“假流程状态”。([GitHub][3])

`20-metrics-evidence.md` 的方向也很正确：不是“代码完成”就算完成，而是必须有 Evidence Bundle；“No Evidence No Done / No Metric No Success”这种原则是熵减核心，因为它把“主观完成”压缩成“可验证完成”。([GitHub][4])

`21-controlled-rsi.md` 也很重要，它把自我改进限制在模板、Prompt、Gate、Matrix 字段、Checklist、Eval 等工程工作流资产上，并禁止自动修改产品目标、安全、隐私、发布、回滚、事故等高风险内容。这个约束能防止 AI 以“自我改进”为名扩大混乱。([GitHub][5])

问题是：**这些好规则现在分布得太散。**

---

## 真正的熵源在哪里

### 1. GoalObject 没有完全唯一的机器 schema

现在文档里已经识别出字段漂移：有的地方用 `id/name/context/...`，有的地方用 `goal_id/title/north_star/success_criteria/current_phase`，Registry 又有自己的字段口径。`24-standard-unification-analysis.md` 明确建议建立唯一 GoalObject schema，并处理 `id` vs `goal_id`、`name` vs `title`、`objective` vs `north_star`、`success_metrics` vs `success_criteria` 等映射关系。([GitHub][1])

这就是你前面说的“同一实体多个别名”。
只不过这里不是业务实体 `User / Member / Account`，而是治理实体：

```txt
Goal
GoalObject
Goal document
Registry goal
Runtime goal
Template goal
```

它们都像是同一个东西，但字段和语义不完全一致。AI 一读，就会开始学习这些差异，最后上下文被“如何兼容别名”塞满。

---

### 2. `status` 被过载

`24-standard-unification-analysis.md` 也指出，状态枚举存在混用：Title Case、uppercase、lowercase/snake_case、metric result、gate result 等都在不同地方出现，并建议拆成 `lifecycle_status`、`runtime_phase`、`gate_result`、`metric_conclusion` 等不同命名空间。([GitHub][1])

这是非常典型的架构熵增：

```yaml
status: Draft
status: GOAL_READY
status: PASS
status: Missing
status: Verified
status: blocked
```

这些都叫 `status`，但其实不是同一个维度。

熵减做法不是继续解释“这里的 status 是什么意思”，而是禁止通用 `status` 泛化使用。

应该改成：

```yaml
goal_lifecycle_status: draft | approved | active | completed | archived
runtime_phase: goal | spec | design | plan | task | prompt | code | test | review | release | retrospective
gate_result: pass | fail | pass_with_risk | not_applicable
metric_conclusion: met | not_met | inconclusive
risk_status: open | mitigated | accepted | closed
```

核心原则：

> 不同状态维度，不得共用一个字段名。

---

### 3. Matrix 有“展示形态”和“机器形态”混用

`09-templates.md` 已经说 Matrix 是横切 traceability artifact，并要求 control-plane Matrix 使用 canonical edge model，旧的宽表只能作为 display/import view，不能直接写入 Matrix control plane。([GitHub][6])

但 `24-standard-unification-analysis.md` 仍然指出 Matrix 还存在历史 display fields、YAML template fields、matrix-gen output、gate-check coverage 之间的漂移。([GitHub][1])

这说明规则已经写了，但还没有完全被“机器化收敛”。

正确方向是只允许一种机器模型：

```yaml
source_id:
target_id:
relation:
status:
evidence_id:
gate_id:
owner:
updated_at:
```

所有宽表都只能是 view：

```txt
Goal | Spec | Task | Code | Test | Evidence
```

宽表不能反过来成为存储格式。

---

### 4. Evidence 协议仍有漂移风险

`24-standard-unification-analysis.md` 指出 Evidence ID、路径、required fields、generator、gate-check 之间曾经存在不一致，并建议统一 Evidence ID、路径、必填字段，让 evidence generator 默认就能通过 gate-check。([GitHub][1])

这类问题很危险，因为 Evidence 是 Goal OS 的“事实层”。
如果 Evidence 自己都有多个协议，那么 Gate 的可信度会下降。

熵减目标应该是：

```txt
Evidence ID 只有一种格式。
Evidence 文件路径只有一种规范。
Evidence required fields 只有一个 schema。
evidence-collect 生成的文件必须天然通过 gate-check。
Gate 不应该再猜 Evidence 是哪种格式。
```

---

### 5. Gate 阈值和 PASS_WITH_RISK 语义需要唯一权威

`04-gates.md` 定义 Gate 编号、名称、顺序、阻塞语义是权威，其他文档只能引用或细化，不能新增 Gate 编号。([GitHub][7])

但 `24-standard-unification-analysis.md` 仍然指出 Gate result、threshold、`PASS_WITH_RISK` 语义、matrix-gen 和 gate-check 阈值之间存在分叉风险，并建议建立唯一 threshold table。([GitHub][1])

这里的熵减方案很简单：

```txt
gate-thresholds.yaml 是唯一阈值来源。
docs 只展示。
gate-check 只读取。
CI 只调用。
Agent 只引用。
```

不要让每个脚本里都藏一份：

```bash
COVERAGE_TARGET=95
```

或者：

```python
MIN_COVERAGE = 0.9
```

这会重新制造半权威。

---

### 6. Runtime 路径存在一个很具体的冲突

这是我看到的一个强烈熵增信号。

`00-authority-map.md` 和 `.config/goal/README.md` 都把 `.config/goal/runtime/` 描述为本地运行态路径或 ignored runtime 区域。([GitHub][2])

但 `goal-validate.py` 又要求 runtime/cache 输出应在 `.config/cache/`，并且把 `.config/goal/runtime/`、`.config/goal/cache/`、`.config/goal/logs` 视为旧路径。([GitHub][8])

这就是架构熵增的典型例子：

```txt
文档权威说 A。
工具权威说 B。
README 又解释一遍。
CI 可能按工具执行。
Agent 读到后不知道该信谁。
```

这必须马上收敛。不能同时保留两套说法。

我的建议是：**顺着当前 validator 收敛**：

```txt
.config/goal/        只放可提交的 control-plane 配置、schema、registry、matrix、evidence index、gate snapshot
.config/cache/goal/  放 transient runtime/cache/log
.omx/state/          放本地 agent 状态
```

但因为 `00-authority-map.md` 是权威入口，所以要用 Change Request 先改权威文档，再改 README、脚本说明和投影。

---

## 熵减的核心改造：Schema First

现在 `docs/goal` 的最小高价值修复，其实它自己已经写出来了：增加 `goal.schema.yaml`、`matrix.schema.yaml`、`evidence.schema.yaml`，统一 ID 文档、模板、matrix-gen、gate-check、evidence-collect、lint 文档和脚本。它还明确说，最重要的是 schema authority，而不是继续堆 prose；一旦 Goal、Matrix、Evidence 的机器 schema 统一，Gate、lint、agent 才会自然收敛。([GitHub][1])

我建议目标结构改成这样：

```txt
docs/goal/
  00-authority-map.md
  CANONICAL-MODEL.md
  schema/
    id.schema.yaml
    goal.schema.yaml
    state.schema.yaml
    matrix-edge.schema.yaml
    evidence.schema.yaml
    gate.schema.yaml
    rule-registry.yaml
  views/
    quickstart.md
    templates.md
    execution-guide.md

.config/goal/
  schema/
    rules.yaml          # generated projection, not hand-written authority
  registry/
  matrix/
  evidence/
  gates/
  pipeline/

.config/cache/goal/
  runtime/
  logs/
  tmp/
```

关键变化是：

```txt
docs/goal/schema/*.yaml  = 权威机器模型
docs/goal/*.md           = 人类解释
.config/goal/*.yaml      = control-plane 投影 / 当前项目状态
tools/*.py, *.sh         = schema 消费者
CI                       = schema 执行者
Agent Context            = schema 摘要
```

不要让 `.md`、`.yaml`、脚本、CI 各自定义一遍规则。

## P0：先做 6 个熵减动作

### P0-1：冻结新增别名

先加一条硬规则：

```txt
任何新字段、新状态、新 Gate、新 Matrix relation、新 Evidence field，
必须先进入 canonical schema。
禁止在模板、脚本、README、CI、Agent Prompt 中私自新增。
```

这条规则要写进：

```txt
00-authority-map.md
10-lint-rules.md
11-ai-collaboration.md
16-ci-cd.md
```

否则 AI 和人类都会继续在局部文件里“顺手补一个字段”。

---

### P0-2：统一 GoalObject

建议选一个 canonical schema，例如：

```yaml
goal_id:
document_version:
title:
context:
objective:
scope:
  in:
  out:
success_criteria:
acceptance_criteria:
constraints:
non_goals:
owner:
priority:
goal_lifecycle_status:
source_refs:
created_at:
updated_at:
```

然后明确废弃映射：

```yaml
deprecated_aliases:
  id: goal_id
  name: title
  north_star: objective
  success_metrics: success_criteria
  current_phase: pipeline.current_phase
  status: goal_lifecycle_status
```

注意：不是让 AI 记住这些别名，而是让 lint 拒绝新代码继续写这些别名。

旧文档可以被 import/convert，新文档不允许继续扩散。

---

### P0-3：禁止裸 `status`

建立 `state.schema.yaml`：

```yaml
allowed_state_fields:
  - goal_lifecycle_status
  - spec_lifecycle_status
  - task_lifecycle_status
  - runtime_phase
  - phase_status
  - workflow_step
  - gate_result
  - matrix_edge_status
  - evidence_status
  - metric_conclusion
  - risk_status
  - release_status
```

然后加 lint：

```txt
除非 schema 明确允许，否则 YAML/JSON 中禁止出现裸 status 字段。
```

这会立刻减少大量语义猜测。

---

### P0-4：Matrix 只保留 canonical edge

Matrix 机器形态只允许：

```yaml
edge_id:
source_id:
target_id:
relation:
matrix_edge_status:
evidence_id:
gate_id:
owner:
updated_at:
drop_reason:
risk_id:
```

宽表只能是展示：

```txt
Goal | Spec | AC | Task | Code | Test | Evidence
```

不允许再出现旧写法直接进入 control plane：

```yaml
goalId:
specId:
taskId:
code_module:
test_case:
```

这和 `09-templates.md` 已有方向一致，只是要把规则从 prose 变成 validator。([GitHub][6])

---

### P0-5：Evidence 生成器和 Gate 检查必须同源

Evidence schema 应该规定：

```yaml
evidence_id:
goal_id:
spec_id:
task_id:
ac_id:
test_id:
evidence_type:
commands_run:
files_changed:
result:
metric_snapshot:
created_at:
owner:
reproducibility:
```

然后强制：

```txt
evidence-collect 生成的 Evidence 必须直接通过 gate-check。
gate-check 不能支持多套历史 Evidence 格式。
旧格式只能通过 migration/import 转换。
```

如果一个 Evidence 需要 Gate 里写兼容分支才能识别，它就是熵源。

---

### P0-6：解决 runtime root 冲突

必须开一个 CR，只做一件事：

```txt
CR: unify runtime/cache path boundary
```

建议选择：

```txt
.config/goal/       committed control plane
.config/cache/goal/ transient runtime/cache/log
.omx/state/         local agent state
```

然后同步修改：

```txt
00-authority-map.md
.config/goal/README.md
tools/README.md
goal-validate.py
goal-workflow.sh
.gitignore
```

验收标准：

```txt
全仓库只剩一个 runtime/cache 口径。
grep ".config/goal/runtime" 只能出现在 migration/deprecated 说明里。
goal-workflow validate 通过。
```

## P1：把规则变成编译链，而不是人肉同步

现在 tools 已经有统一入口：`goal-workflow.sh` 负责 preflight、validate、gate、ci、release 等流程，tools README 也要求优先使用 workflow 入口，而不是直接调用底层脚本。([GitHub][9])

下一步应该把它升级成：

```txt
schema -> generated rules -> templates -> examples -> tools -> CI
```

也就是：

```bash
goal-workflow schema-check
goal-workflow generate-projections
goal-workflow validate
goal-workflow gate
goal-workflow ci
```

其中 `generate-projections` 做这些事：

```txt
从 docs/goal/schema/*.yaml 生成：
- .config/goal/schema/rules.yaml
- docs/goal/GLOSSARY 部分术语
- 09-templates 里的 YAML template
- lint rule registry
- gate threshold table
- agent context summary
```

这样以后改一个字段，不需要手动改 7 个地方。

熵减的本质是：

```txt
人只改一处。
机器负责投影。
投影漂移即失败。
```

## P1：建立 Rule Registry

目前 `10-lint-rules.md` 写了很多规则，`24-standard-unification-analysis.md` 也指出脚本只实现了其中一部分，需要一个 rule registry 区分 implemented、manual、planned，并输出覆盖报告。([GitHub][1])

建议建：

```yaml
rules:
  - rule_id: GOAL_FIELD_001
    name: no_deprecated_goal_fields
    target: goal.schema.yaml
    severity: error
    source_doc: docs/goal/schema/goal.schema.yaml
    checker: goal-validate.py
    implementation_status: implemented

  - rule_id: STATE_001
    name: no_unqualified_status
    target: "*.yaml"
    severity: error
    source_doc: docs/goal/schema/state.schema.yaml
    checker: lint-goal.sh
    implementation_status: implemented

  - rule_id: MATRIX_001
    name: canonical_edge_only
    target: ".config/goal/matrix/*.yaml"
    severity: error
    source_doc: docs/goal/schema/matrix-edge.schema.yaml
    checker: matrix-gen.py
    implementation_status: implemented
```

然后 CI 输出：

```txt
Rules defined: 120
Rules implemented: 87
Manual review: 21
Planned: 12
Coverage: 72.5%
```

没有这个 registry，文档规则越多，AI 越难知道哪些是真规则，哪些只是愿景。

## P2：给 AI 一个压缩后的上下文包

现在 `11-ai-collaboration.md` 已经定义了 AI Context Package，要给 AI Goal summary、Spec summary、Matrix edge、Task、代码结构、接口、数据模型、约束、测试和禁止事项。([GitHub][10])

但我建议再加一个更硬的文件：

```txt
docs/goal/AI-GOAL-CONTEXT.md
```

只保留 AI 必须知道的 canonical 规则：

```txt
1. 只信 schema，不从模板反推字段。
2. GoalObject 使用 goal.schema.yaml。
3. Matrix 只使用 canonical edge。
4. Evidence 只使用 evidence.schema.yaml。
5. Gate result 只使用 gate.schema.yaml。
6. 禁止裸 status。
7. 禁止新增 ID 格式。
8. 禁止新增 runtime root。
9. 遇到未知情况，标记 Hypothesis，不得编造规则。
10. 涉及 Gate/Release/Rollback/Incident/Security/Privacy，必须走 CR。
```

这样 AI 不需要每次读完整 `docs/goal`。
它只需要读：

```txt
00-authority-map.md
CANONICAL-MODEL.md
schema/*.yaml
AI-GOAL-CONTEXT.md
当前任务 Context Package
```

这会显著减少上下文噪声。

## 最重要的原则

不要再加一层“解释文档”来解决这个问题。

`docs/goal` 现在的熵，不是因为解释不够，而是因为解释太多、权威太多、字段太多、状态太多。

真正的熵减是：

```txt
一个实体，一个 schema。
一个字段，一个含义。
一个状态，一个命名空间。
一个 Gate，一个阈值来源。
一个 Evidence 协议。
一个 Matrix 机器模型。
一个 runtime root。
一个 workflow 入口。
```

对 AI 来说，最关键的是这句：

> **不要让 AI 从历史复杂性里学习架构；让 AI 从 canonical schema 里学习架构。**

现在 `docs/goal` 已经有了很好的方向：SSOT、Gate、Evidence、Matrix、Controlled RSI 都在。下一步不是继续扩大 Goal OS，而是把它收敛成一个可编译、可验证、可拒绝漂移的系统。

继续的话，我会把它推进到**真正可执行的熵减方案**，而不是继续泛泛讲“要统一”。

当前 `docs/goal` 已经有一个很好的骨架：`00-authority-map.md` 明确说它只定义“哪里是权威、哪里是投影”，并要求 README、SOP、Runtime、CI、schema、示例状态文件只能引用、校验或投影 SSOT，不得定义新的枚举；`03-pipeline.md` 也已经把主流程固定为 11 层，并明确 Matrix 是横切追溯制品，不是主流程阶段。([GitHub][1])

但问题是：`24-standard-unification-analysis.md` 已经指出 Goal 体系现在不是缺标准，而是多个标准面并存，ID、Goal schema、状态枚举、Matrix、Evidence、Gate 和工具实现都还有不同程度漂移；它给出的综合结构统一度是 66/100。([GitHub][2])

所以接下来要做的不是“再写一个解释文档”，而是做一组**收敛 PR**。

---

# 第一阶段：先止血，不允许继续造别名

第一阶段目标只有一个：

> **从今天开始，不允许新增半权威。**

也就是，不允许在模板、脚本、README、CI、Agent prompt 里局部新增字段、状态、Gate、Evidence 口径、Matrix 字段。

可以先加一条最高优先级规则：

```md
## Canonical Change Rule

Any change to GoalObject fields, ID grammar, state enum, Gate result,
Matrix edge schema, Evidence schema, runtime root, or rule severity MUST
first update the canonical schema or authority document.

Templates, README, CI, runtime scripts, examples, and agent prompts MUST NOT
introduce local variants.

If a local variant is needed for compatibility, it MUST be represented as:
- deprecated alias
- migration rule
- explicit validator warning/error
```

这条规则应该写进：

```txt
docs/goal/00-authority-map.md
docs/goal/10-lint-rules.md
docs/goal/25-execution-guide.md
docs/goal/11-ai-collaboration.md
```

原因很简单：`00-authority-map.md` 已经规定修改状态、Gate、ID、Registry、Evidence 或 Matrix 口径时要先改权威文档，再同步投影；现在要把这句话升级成一个可执行的“禁止本地定义规则”。([GitHub][1])

# 第二阶段：先修一个具体冲突：runtime root

这是最适合第一个 PR 的熵减点，因为它非常具体。

当前 README 里说 `.config/goal/` 是控制面目录，并且把本地运行态、锁、缓存、local 覆盖和日志写到 `.config/goal/runtime/`、`.omx/state/` 或 ignored 目录。([GitHub][3])

但 `goal-validate.py` 已经在执行另一条规则：`.gitignore` 必须包含 `.config/cache/`，`.config/goal/` 必须可追踪，并且 `.config/goal/runtime/`、`.config/goal/cache/`、`.config/goal/logs/` 会被视为旧 runtime/cache/log root。([GitHub][4])

这就是典型熵增：

```txt
README 说 A。
validator 执行 B。
Agent 读到 A 和 B 后不知道该信谁。
```

这个要第一时间收敛。

我建议直接顺着 validator 收敛，因为它已经是可执行检查：

```txt
.config/goal/        = 可提交 control plane
.config/cache/       = 本地 runtime/cache/log
.omx/state/          = agent local state / recovery state
```

第一个 PR 可以叫：

```txt
CR-GOAL-ENTROPY-001: unify runtime/cache boundary
```

改动范围：

```txt
docs/goal/README.md
docs/goal/00-authority-map.md
docs/goal/12-operations.md
docs/goal/13-runtime-engine.md
docs/goal/tools/README.md
.config/goal/README.md
.gitignore
```

验收标准：

```bash
grep -R "\.config/goal/runtime" docs/goal .config/goal .github .claude .codex .copilot
```

只允许出现在：

```txt
deprecated / migration / historical note
```

不允许出现在当前规则里。

# 第三阶段：建立 canonical schema，不要继续靠 prose 同步

`24-standard-unification-analysis.md` 已经明确建议：新增 `docs/goal/schema/goal.schema.yaml`、`matrix.schema.yaml`、`evidence.schema.yaml`，并同步 ID、模板、工具、lint；它还判断最该先修的不是文档表达，而是 schema 权威化。([GitHub][2])

所以第二个 PR 应该叫：

```txt
CR-GOAL-ENTROPY-002: introduce canonical schemas
```

建议新增：

```txt
docs/goal/schema/
  id.schema.yaml
  goal-object.schema.yaml
  state.schema.yaml
  matrix-edge.schema.yaml
  evidence.schema.yaml
  gate.schema.yaml
  gate-thresholds.yaml
  rule-registry.yaml
```

注意：这些 schema 不是“又一套文档”，而是**机器权威**。
`.config/goal/schema/rules.yaml` 应该变成它们的 projection，而不是人工手写的另一个权威面。

目标结构应该是：

```txt
docs/goal/schema/*.yaml
    ↓ generate / validate
.config/goal/schema/rules.yaml
    ↓ consumed by
goal-validate.py
matrix-gen.py
gate-check.sh
evidence-collect.sh
lint-goal.sh
goal-workflow.sh
CI
Agent Context Package
```

换句话说：

```txt
人只改 schema。
工具消费 schema。
文档展示 schema。
CI 阻断 schema 漂移。
AI 只读 schema 摘要。
```

# 第四阶段：统一 GoalObject

`24-standard-unification-analysis.md` 指出，Goal 字段现在有明显漂移：`02-goal-standard.md` 使用 `id/name/objective/success_metrics/status` 等字段，模板又缺少部分字段并使用嵌套 scope，Registry 使用 `goal_id/title/north_star/success_criteria/current_phase`。([GitHub][2])

这就是你前面说的“同一实体多个别名”。

建议 canonical schema 定成这样：

```yaml
schema_id: goal-object.schema.yaml
version: v1

canonical_object: GoalObject

required:
  - goal_id
  - title
  - context
  - objective
  - success_criteria
  - acceptance_criteria
  - scope
  - constraints
  - non_goals
  - owner
  - priority
  - goal_lifecycle_status

fields:
  goal_id:
    type: string
    pattern_ref: id.goal

  title:
    type: string

  context:
    type: string

  objective:
    type: string

  success_criteria:
    type: array
    items: MetricOrCriterion

  acceptance_criteria:
    type: array
    items: AcceptanceCriterion

  scope:
    type: object
    required:
      - in
      - out
    properties:
      in:
        type: array
      out:
        type: array

  constraints:
    type: array

  non_goals:
    type: array

  owner:
    type: string

  priority:
    enum:
      - P0
      - P1
      - P2
      - P3

  goal_lifecycle_status:
    enum_ref: state.goal_lifecycle_status

deprecated_aliases:
  id: goal_id
  name: title
  north_star: objective
  success_metrics: success_criteria
  status: goal_lifecycle_status
  current_phase: runtime_phase
```

关键点是：**deprecated alias 只用于 migration，不允许新文件继续使用。**

validator 里应该分两步：

```txt
Phase 1:
  deprecated alias = WARN

Phase 2:
  deprecated alias = ERROR

Phase 3:
  migration 完成后删除 alias 支持
```

不能一开始就让所有旧文件 fail，否则会导致 AI/人类为了“快速通过”又写兼容分支，反而熵增。

# 第五阶段：拆掉裸 `status`

`24-standard-unification-analysis.md` 指出状态枚举混杂：Goal 生命周期、Runtime phase、Registry、Metric Validation、Gate result 都在使用不同风格的状态值，并建议拆成 `lifecycle_status`、`runtime_phase`、`gate_result`、`metric_conclusion` 等字段。([GitHub][2])

但这里不能粗暴地“全仓库替换 status”，因为当前 Matrix canonical edge 和 validator 仍在使用 `status` 字段；`09-templates.md` 的 Matrix edge 表头包含 `status`，`goal-validate.py` 的 `EDGE_REQUIRED_FIELDS` 也要求 `status`。([GitHub][5])

所以实际迁移要分阶段：

## 先定义状态命名空间

```yaml
state_namespaces:
  goal_lifecycle_status:
    values:
      - draft
      - approved
      - active
      - completed
      - archived
      - rejected

  pipeline_state:
    values:
      - INIT
      - CONTEXT_READY
      - GOAL_READY
      - SPEC_READY
      - DESIGN_READY
      - PLAN_READY
      - TASKS_READY
      - EXECUTING
      - VERIFYING
      - REVIEWING
      - RELEASING
      - RETROSPECTING
      - DONE

  current_phase:
    values:
      - GOAL
      - SPEC
      - DESIGN
      - PLAN
      - TASKS
      - PROMPT
      - CODE
      - TEST
      - REVIEW
      - RELEASE
      - RETROSPECTIVE

  phase_status:
    values:
      - NOT_STARTED
      - IN_PROGRESS
      - IN_REVIEW
      - READY
      - DONE
      - BLOCKED
      - SKIPPED
      - STALE

  gate_result:
    values:
      - PASS
      - PASS_WITH_RISK
      - FAIL
      - BLOCKED

  matrix_edge_status:
    values:
      - Unmapped
      - Mapped
      - Linked
      - Verified
      - Dropped
      - Drifted
      - Stale
      - Blocked
      - Changed

  metric_conclusion:
    values:
      - validated
      - partially_achieved
      - not_achieved
      - invalid_metric
      - inconclusive
```

`03-pipeline.md` 已经把 `pipeline_state`、`current_phase`、`phase_status`、`workflow_step` 四个轴拆开了，这个方向是对的；下一步是把这个模式扩展到 Goal、Gate、Matrix、Evidence 和 Metric。([GitHub][6])

## 再做兼容映射

```yaml
migration:
  matrix:
    status:
      canonical: matrix_edge_status
      phase: warn
      remove_after: v2
```

短期内 validator 可以接受：

```yaml
status: Verified
```

但输出 warning：

```txt
GV-STATE-DEPRECATED-STATUS:
matrix edge uses deprecated field "status"; use "matrix_edge_status".
```

最终 Matrix edge schema 应该变成：

```yaml
required:
  - source_id
  - target_id
  - relation
  - matrix_edge_status
  - evidence_id
  - gate_id
  - owner
  - updated_at
```

这样 AI 以后看到字段名就知道这是 Matrix edge 的状态，而不是 Goal、Gate、Pipeline 或 Metric 的状态。

# 第六阶段：Matrix 只保留 edge model

这一点其实已经做了一半。

`09-templates.md` 已经写明：进入 `.config/goal/matrix/`、Gate、validator、CI 或 Release 控制面的 Matrix 必须使用 canonical edge model；旧宽表只能作为展示或导入视图，进入控制面前必须转换。([GitHub][5])

`goal-validate.py` 也已经开始检查 canonical edge：它要求 `source_id`、`target_id`、`relation`、`status`、`evidence_id`、`gate_id`、`owner`、`updated_at`，并会报错 legacy flat-traceability fields。([GitHub][4])

下一步不是改理念，而是把 schema 外置：

```yaml
schema_id: matrix-edge.schema.yaml
version: v1

required:
  - edge_id
  - source_type
  - source_id
  - relation
  - target_type
  - target_id
  - matrix_edge_status
  - gate_id
  - owner
  - updated_at

optional:
  - evidence_id
  - risk_id
  - drop_reason
  - priority

relations:
  - decomposes_to
  - contains
  - accepted_by
  - planned_by
  - implemented_by
  - prompted_by
  - verified_by
  - evidenced_by

terminal_statuses:
  releasable:
    - Verified
  releasable_with_explanation:
    - Dropped

rules:
  - if: matrix_edge_status == Verified
    require:
      - evidence_id

  - if: matrix_edge_status == Dropped
    require:
      - drop_reason
```

然后 `goal-validate.py` 不再硬编码 `EDGE_REQUIRED_FIELDS`、`EDGE_STATUSES`、`EDGE_RELATIONS`，而是从 schema 加载。
这一步很关键：**字段从代码里搬出来，代码只做执行器。**

# 第七阶段：Evidence 生成器必须天然通过 Gate

Evidence 是整个 Goal OS 的事实层。
如果 Evidence 也有多个协议，Gate 就会变成“猜格式”。

`24-standard-unification-analysis.md` 指出 Evidence 当前有明显漂移：ID 绑定对象不一致，路径布局不一致，必填字段不一致，`evidence-collect.sh` 生成物不稳定包含 `Test ID` 和 `Commands Run`，但 `gate-check.sh` 又要求这些字段。([GitHub][2])

所以 Evidence schema 应该先定：

```yaml
schema_id: evidence.schema.yaml
version: v1

required:
  - evidence_id
  - evidence_type
  - goal_id
  - task_id
  - test_id
  - matrix_edge_ids
  - status
  - commands_run
  - files_changed
  - environment
  - commit
  - created_at
  - owner
  - result_summary

fields:
  evidence_id:
    pattern: EVID-<task-id>-<test-ref>-NNN

  evidence_type:
    enum:
      - test_output
      - review_record
      - command_log
      - coverage_report
      - release_manifest
      - metrics_snapshot
      - rollback_validation

  status:
    enum:
      - PASS
      - FAIL
      - BLOCKED
      - INCONCLUSIVE

  commands_run:
    type: array
    min_items: 1

  files_changed:
    type: array

  matrix_edge_ids:
    type: array
```

然后改工具规则：

```txt
evidence-collect.sh 只能生成 evidence.schema.yaml 允许的字段。
gate-check.sh 只能接受 evidence.schema.yaml 允许的字段。
旧 Evidence 格式必须通过 migration 转换，不允许 Gate 里写多套兼容逻辑。
```

这句话很重要：

> Gate 不应该理解历史格式；migration 才应该理解历史格式。

否则 Gate 会变成垃圾桶，越来越复杂。

# 第八阶段：Gate 阈值单源化

`04-gates.md` 是 G0-G11 编号、名称、顺序和阻塞语义的权威来源，并明确其他文档不能新增独立 Gate 编号。([GitHub][7])

但 `24-standard-unification-analysis.md` 指出 Gate 仍有几个漂移点：`PASS_WITH_RISK` 是否允许进入下一阶段、advisory score 和 hard gate 的区别、每个 Gate 的阈值表、工具阈值与文档阈值分叉。([GitHub][2])

建议建立：

```yaml
schema_id: gate-thresholds.yaml
version: v1

gates:
  G1:
    name: Goal Gate
    blocking: true
    result_field: gate_result
    pass:
      min_goal_score: 80
    pass_with_risk:
      allowed: true
      requires:
        - risk_id
        - owner
        - mitigation
        - due_at

  G5:
    name: Task / Matrix Gate
    blocking: true
    pass:
      release_critical_edge_coverage: 0.95
      orphan_edges: 0
    pass_with_risk:
      allowed: true
      requires:
        - risk_id
        - risk_owner
        - mitigation
        - due_at

  G6:
    name: Implementation Gate
    blocking: true
    pass_with_risk:
      allowed: false

  G10:
    name: Release Gate
    blocking: true
    pass:
      matrix_releasable_coverage: 0.95
      open_release_blocking_risks: 0
      evidence_bundle_required: true
      rollback_validation_required: true
    pass_with_risk:
      allowed: false
```

然后所有工具都只读这一个文件：

```txt
gate-check.sh
goal-validate.py
goal-release-gate.sh
goal-workflow.sh
CI
```

`goal-validate.py` 现在已经硬编码了 `GATE_DECISION_STATUSES` 和 `PASS_WITH_RISK_DISALLOWED = {"G6", "G10"}`，这说明工具层已经有收敛意图，但还没有完全外置成 schema。([GitHub][4])

# 第九阶段：Rule Registry，解决“文档规则多、工具只实现一部分”

`24-standard-unification-analysis.md` 指出，`10-lint-rules.md` 规则文档完整，但脚本只实现子集，缺少完整字段 schema 校验、状态枚举校验、ID grammar 校验；它建议建立机器可读 rule registry，标注 `rule_id`、`severity`、`target_object`、`checker`、`docs_ref`，并区分 `implemented`、`manual`、`planned`。([GitHub][2])

建议 `rule-registry.yaml` 长这样：

```yaml
schema_id: rule-registry.yaml
version: v1

rules:
  - rule_id: GOAL_SCHEMA_001
    title: GoalObject must use canonical fields
    target_object: GoalObject
    source_schema: docs/goal/schema/goal-object.schema.yaml
    severity: error
    checker: goal-validate.py
    implementation_status: implemented

  - rule_id: STATE_001
    title: No unqualified status outside compatibility windows
    target_object:
      - GoalObject
      - RegistryItem
      - MatrixEdge
      - Evidence
      - Gate
    source_schema: docs/goal/schema/state.schema.yaml
    severity: warn
    checker: goal-validate.py
    implementation_status: planned
    migration_phase: phase_1_warn

  - rule_id: MATRIX_001
    title: Matrix control plane must use canonical edge model
    target_object: MatrixEdge
    source_schema: docs/goal/schema/matrix-edge.schema.yaml
    severity: error
    checker: goal-validate.py
    implementation_status: implemented

  - rule_id: EVIDENCE_001
    title: Evidence collector output must pass Evidence Gate
    target_object: Evidence
    source_schema: docs/goal/schema/evidence.schema.yaml
    severity: error
    checker:
      - evidence-collect.sh
      - gate-check.sh
    implementation_status: planned

  - rule_id: RUNTIME_001
    title: Runtime cache must not live under .config/goal
    target_object: RuntimeBoundary
    severity: error
    checker: goal-validate.py
    implementation_status: implemented
```

然后 CI 输出：

```txt
Rule registry summary:
- total rules: 48
- implemented: 21
- manual: 12
- planned: 15
- executable coverage: 43.75%
```

这能防止文档继续“看起来很强”，但工具实际没法阻断。

# 第十阶段：把 AI Context 压缩成 canonical context

`11-ai-collaboration.md` 已经要求 AI 不要只拿 Task，而要拿 Context Package，包括 Goal 摘要、Spec 摘要、Matrix edge、当前 Task、代码结构、接口、数据模型、约束、测试要求和禁止事项。([GitHub][8])

这很好，但还不够。

因为对于架构熵减来说，AI 还需要一个更短、更硬的上下文：

```txt
AI-GOAL-CANONICAL-CONTEXT.md
```

内容不超过 100 行：

```md
# AI Goal Canonical Context

## Trust order

1. CONSTITUTION.md
2. docs/goal/00-authority-map.md
3. docs/goal/schema/*.yaml
4. .config/goal/schema/rules.yaml
5. current Goal / Spec / Matrix / Evidence files
6. templates and README

Templates are examples, not authority.

## Canonical objects

- GoalObject: docs/goal/schema/goal-object.schema.yaml
- MatrixEdge: docs/goal/schema/matrix-edge.schema.yaml
- Evidence: docs/goal/schema/evidence.schema.yaml
- Gate: docs/goal/schema/gate.schema.yaml
- State: docs/goal/schema/state.schema.yaml
- ID grammar: docs/goal/schema/id.schema.yaml

## Hard rules

- Do not introduce new GoalObject fields.
- Do not introduce new ID grammar.
- Do not introduce new Gate IDs.
- Do not introduce new status fields.
- Do not add runtime/cache/log roots under .config/goal.
- Do not write Matrix as a workflow phase.
- Do not write Evidence in a format gate-check cannot validate.
- Do not relax Gate, Test, Evidence, Release, Rollback, Security, Privacy, P0/P1 AC.
- Unknown facts must be marked Hypothesis.
- Protected assets require Change Request.

## Deprecated aliases

- id -> goal_id
- name -> title
- north_star -> objective
- success_metrics -> success_criteria
- status -> specific namespaced status
- matrix.status -> matrix_edge_status

New files must not use deprecated aliases.
```

这样 AI 不需要每次读 25 个文档再“理解系统”。
它只需要先读 authority、schema、canonical context，再读当前任务上下文。

这就是对 AI 的上下文熵减。

# 不要做的事

这里特别重要。

## 1. 不要再新增一个“统一说明文档”

因为 `24-standard-unification-analysis.md` 已经说了：问题不是缺少标准，而是多个标准面并存。继续加说明，只会多一个标准面。([GitHub][2])

## 2. 不要让 Gate 兼容所有历史格式

历史格式应该 migration，不应该让 `gate-check.sh` 长出一堆：

```bash
if old_format
elif legacy_format
elif chinese_heading_format
elif registry_format
```

Gate 是阻断器，不是考古学家。

## 3. 不要让 AI 自己读全仓库归纳规则

`25-execution-guide.md` 要求首次执行先读 authority、README、pipeline、gates、layer standards、metrics evidence、risk decisions、agent protocols、controlled RSI，并且无法验证的内容必须标记为 Hypothesis。([GitHub][10])

这个顺序没问题，但 AI 真正写代码/改文档时，需要更短的 canonical context。否则它会读到大量历史兼容说明，然后把兼容说明当成可继续扩展的架构模式。

## 4. 不要自动放宽 Gate / Evidence / Release

`21-controlled-rsi.md` 明确禁止 RSI 自动修改已批准 Goal 的核心目标、P0/P1 验收标准、安全、隐私、资金、权限、数据保留约束、发布 Gate、回滚要求、事故处理要求、生产代码、失败测试、证据要求等；这类变更必须走显式 CR。([GitHub][11])

所以这次熵减只能做：

```txt
字段收敛
schema 外置
投影生成
漂移检测
旧格式 migration
```

不能做：

```txt
降低 Gate
删除 Evidence 要求
放宽 Release 阻断
改变 P0/P1 AC
```

# 一句话继续总结

`docs/goal` 现在要做的熵减，不是缩小愿景，而是**压缩权威面**：

```txt
多个字段名 → 一个 GoalObject schema
多个 status → 多个命名清晰的状态轴
多个 Matrix 形态 → 一个 edge model
多个 Evidence 协议 → 一个 evidence schema
多个 Gate 阈值 → 一个 threshold table
多个命令入口 → 一个 goal-workflow
多个 AI 解释路径 → 一个 canonical context
多个 runtime 目录口径 → 一个 runtime boundary
```

先做 runtime boundary，因为它最小、最确定、最容易证明。然后再做 schema skeleton、GoalObject、State、Evidence、Rule Registry。这样每个 PR 都是在减少“AI 未来必须记住的例外”。
