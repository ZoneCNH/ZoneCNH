# ZoneCNH 25 模块完整修复与生产重新认证计划

> 版本：v1.0-draft  
> 日期：2026-07-11  
> 上游基线：`ZoneCNH_25_modules_production_release_standard_v1.0.md`  
> 适用目录：`/home/workspace/{module}`  
> 目标：把 25 个模块从“版本、CI、Evidence 与实现事实不一致”修复为可验证、可发布、可被真实消费者采用的生产级模块。

---

## 0. 最终裁决

本计划不把 25 个仓库同时改绿，而是按信任依赖顺序修复：[INFERRED, HIGH]

```text
W0 事实冻结
 → W1 标准控制平面
 → W2 三类 canary
 → W3 L0/L1/Assembly/Test
 → W4 存储适配器
 → W5 contracts/transportx/L2.5
 → W6 全舰队重新认证
```

任何模块只有满足以下 release tuple 才能重新标记为生产级：

```text
candidate commit/tree
+ successful required CI
+ class-specific verification
+ canonical Evidence + sidecar hash
+ immutable tag
+ GitHub Release + required assets
+ downstream adoption
+ live/fault/soak（适用时）
```

时间不是放行条件。30 天目标是完成控制平面、三个 canary、P0 修复和最接近模块的重新认证；全 25 仓生产重新认证按 60–90 天规划。

## 1. 全局执行规则

### 1.1 分支与工作区

- `/home/workspace/{module}` 只保留 clean main checkout。
- 每个工作包使用独立 worktree：`/home/workspace/{module}/.worktree/workspaces/{type}/{module}-{slug}`。
- 分支必须从最新 `origin/main` 创建；禁止 main 直接编辑、提交或实验。
- 每个 PR 只承担一个可回滚目标，P0 实现修复与治理批量同步不得混在同一 PR。
- release/preflight 强制 `GOWORK=off`、`GOTOOLCHAIN=local`、`GOFLAGS=-mod=readonly -trimpath`。

### 1.2 工作包状态

| 状态          | 含义                                     |
| ------------- | ---------------------------------------- |
| `BLOCKED`     | 前置事实或依赖尚未满足                   |
| `READY`       | Goal/Spec/AC/TC 和前置依赖完整           |
| `IN_PROGRESS` | 已创建 worktree/branch，只有一个 owner   |
| `VERIFIED`    | PR head 的测试与 Evidence 已通过         |
| `RELEASED`    | tag、Release、assets 与 Evidence 一致    |
| `QUALIFIED`   | adoption 和适用的 live/fault/soak 已通过 |

### 1.3 每个 PR 的强制输出

1. Goal/Task ID。
2. 修改范围与明确非目标。
3. 受影响的 API/schema/config/error/metric。
4. 新增或更新的 AC/TC。
5. 机器结果：format、mod、build、vet、lint、test、race、coverage、boundary、security。
6. 模块特有结果：property/fuzz/model/integration/live/fault/soak/conformance。
7. Evidence：commit、tree、run、toolchain、service/image digest、artifact hash。
8. SemVer 裁决与迁移说明。
9. 回滚方案。

### 1.4 共同修复基线

所有模块都要完成以下 `BASE-*` 工作包；由 `xlib_harness` 生成，模块仓只填 profile 差异。

| ID       | 工作包       | 完成条件                                                                       |
| -------- | ------------ | ------------------------------------------------------------------------------ | -------------------- |
| BASE-001 | 身份统一     | repo ID、repository、module path、package、repo-contract 一致                  |
| BASE-002 | Go 基线      | `go 1.26.0`、toolchain `go1.26.5`；例外有 ADR                                  |
| BASE-003 | 仓库文件     | README/LICENSE/SECURITY/CHANGELOG/CONTRIBUTING/CODEOWNERS/profile 必备文件齐全 |
| BASE-004 | 生成式 CI    | workflow 来自锁定 standard bundle；零手工削弱                                  |
| BASE-005 | 供应链       | Actions 40 位 SHA；无 `latest`、`curl                                          | sh`、非阻断 security |
| BASE-006 | API/版本事实 | main=`unreleased/next`；released tuple 完全一致；无倒挂常量                    |
| BASE-007 | Evidence     | 每个 gate 上传结构化 result；最终 manifest 绑定 commit/tree/run                |
| BASE-008 | Release      | candidate SHA final check 后才创建稳定 tag；Release assets 非空                |
| BASE-009 | Adoption     | `go get @tag` + 至少一个消费者；contracts 至少两个                             |

## 2. 总体依赖与修复波次

### 2.1 波次计划

| 波次 | 模块                                                                         | 退出条件                                                            |
| ---- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------- |

### 2.2 并行原则

- W1 内可并行实现四仓，但 schema/CLI contract 必须先串行冻结。

- W4 可按 light/heavy pool 并行，但每个真实服务一次只跑一个重型 soak。
- W5 中 decimalx 已是前置；domainx 先于 domain_market/domain_macro，三者先于 domain_exchange；contracts/transportx 与领域映射协调发布。

## 4.4 `resiliencx`

## 8. 发布与重新认证 Runbook

### 8.1 Candidate 阶段

1. 从 protected main SHA 创建 release candidate record，不先创建稳定 tag。
2. 执行 `release-final-check`：identity、Go、API/SemVer、security、class verification、Evidence。
3. 生成待发布 assets、SBOM、provenance 和 hashes。
4. 对 CLI 构建支持平台二进制；library 生成 API snapshot、source digest、consumer fixture。
5. 所有结果绑定候选 commit/tree。

### 8.2 Stable 阶段

1. 同一个受信 workflow 创建 annotated/signed stable tag。
2. 验证 tag SHA == candidate SHA，Evidence digest 未变化。
3. 创建 GitHub Release，上传全部 required assets。
4. 验证 assets 数量、名称、digest、SBOM、provenance。
5. 执行 `GOWORK=off go get module@tag` 和 consumer compile。
6. 外部 adapter 执行 tag fail-closed live；风险触发 fault/soak。

### 8.3 Qualification 阶段

- 合格：adoption/live/fault/soak 满足 profile。
- Quarantined：Release 已存在，但 consumer/live 失败；保留 tag，不改写历史。
- Revoked：发现严重漏洞/错误契约；发布 advisory 和修复版本，不删除 tag。
- Requalified：新证据恢复当前资格。

### 10.2 Compound Engineering 闭环

```text
模块缺陷
→ regression/negative fixture
→ 模块修复
→ xlib_standard policy/template
→ xlibgate reason code
→ xlib_harness fleet sync
→ xlib_evidence fact field
→ 全仓历史扫描
```

### 10.3 AutoResearch / Self-improving

- 新 gate 先在 kernel/redisx/domain_market 三 canary Shadow。
- 以 false-pass、escaped defect、mutation、flake、CI cost 评估，不以 gate 自身分数自证。
- threshold 调整必须 A/B + outer metrics + 人工批准。
- 自动 PR 可以修漂移，但不得自动降低门禁或直接写 main。
- 每个 waiver 有 owner、reason、补偿措施、expiry；到期自动失败。

## 11. 最终推荐执行路径

```text
先修“判断系统”
  xlib_standard → xlibgate → xlib_evidence → xlib_harness

再用三类 canary 证明判断系统
  kernel → decimalx → redisx

再修基础运行时和真实外部系统
  L1 → storage → bootstrap

最后修稳定语义与下游迁移
  domainx → domain_market/domain_macro → domain_exchange
  → contracts → transportx → consumers
```

最不应该做的路径是：批量修改版本号、补几个绿色 badge、把状态 JSON 改成 true，然后继续发布。正确路径是把每一个“完成”都绑定到不可变 commit、真实验证对象和可重放 Evidence。
