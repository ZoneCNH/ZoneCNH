### 2.2 关键结论

`[KNOWN]` HIGH：本项目实际定位（`README.md:1-15`）是 **Binance Market Data C/S Module（行情采集 + ingest 验收）**，是市场数据采集/分发基础设施，**不是通用交易所 SDK**。

- **交易功能（下单/撤单/余额）存在但非主路径**：`pkg/binancex/adapter.go` 作为 `domainexchange.VenueAdapter` 的可复用实现存在，给上游 `orderx`/`x.go` 用，本仓 `internal/` 和 `cmd/` 中无任何调用方。
- **签名认证**：本项目层面无自研 HMAC 签名，完全委托 binance-connector-go SDK；`crypto/sha256` 仅用于幂等键和校验和（`idempotency.go:50`、`ingest.go:203`）。
- **核心运行时功能**：K线/深度/WS/exchangeInfo/白名单/历史回填/DLQ 这 7 项是真正的运行时主路径，实现完整。
- **合约下单**：`SupportsFutures=true` 是**夸大声明**——UM/CM 端点仅用于行情采集和历史回填，无任何合约下单/持仓/杠杆代码。

## 5. 关键发现汇总与修复优先级

跨 4 路分析综合，按修复优先级排序：

### 🔴 P0 — 无

### 🟠 P1（4 项，需优先处理）

1. **节流基础设施是死代码**（§3.3）`[KNOWN]` HIGH
   - `throttle.go` 的 `Allow`/`RecordSuccess`/`RecordBackoff` + `reliability.go` 的 `WeightGate.Admit` 在生产代码零调用。FR-025 声称的 80/20 预算 + AIMD 自适应限流**未接入实际请求路径**。
   - 影响：生产环境无客户端侧限频保护，可能触发 Binance IP 封禁。
   - 修复：在 `spot.go`/`history_rest.go` 每次请求前 `throttle.Allow(kind, weight)`，2xx 后 `RecordSuccess`，429/-1003 后 `RecordBackoff`。

2. **未消费 Binance weight 限频信号**（§3.3）`[KNOWN]` HIGH
   - 全仓零读取 `X-MBX-USED-WEIGHT-1M` 响应头，AIMD 无输入信号。
   - 修复：在 HTTP 响应处读取该头并 feed 给 ThrottleManager。

3. **`decimalx.MustFromString` 用于外部 SDK 返回字段**（§3.1）`[KNOWN]` HIGH
   - `adapter.go` 9 处未加固，Binance 返回空串/异常格式即进程 panic。开发者已在 `:500` 为 `exQty` 加守卫，证明已知风险。
   - 修复：全部改用返回 error 的 `decimalx.Parse`/`TryFromString`，或封装守卫函数。

4. **TDengine SQL 手工转义而非参数化**（§3.6）`[KNOWN]` MED
   - `history_reader.go:62` 用 `escapeTaos`（仅处理单引号）拼接外部输入（HTTP path param）。
   - 修复：迁移到 TDengine 参数化接口，或叠加正则白名单 `^[A-Z0-9]{1,32}$`。

### 🟡 P2（3 项）

1. 429 重试忽略 `Retry-After` 头（`history_rest.go:227`）
2. `SubmitOrder` decimal→float64 精度损失（`adapter.go:136/149/159`，SDK 限制）
3. API 层 `symbol`/`pl` 缺格式白名单（`query.go`/`analytics.go`），放大下游 SQL 风险
