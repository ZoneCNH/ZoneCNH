# Go 量化交易 SOLID 完整规则定义

---

## S — 单一职责原则 (Single Responsibility Principle)

### 核心定义

> 每个包、结构体、函数只负责一个业务职责，只有一个引起变化的原因

### 规则列表

**包级别**

- `S-PKG-01` 每个包只表达一个领域概念，包名即职责声明
- `S-PKG-02` 禁止出现 `utils`、`common`、`misc` 等无语义包名
- `S-PKG-03` 包的对外导出符号必须围绕同一个职责主题
- `S-PKG-04` 基础设施代码必须与业务逻辑代码隔离在不同包中

**结构体级别**

- `S-STR-01` 每个结构体只承担一个业务角色，字段数超过 8 个时必须审查是否违反职责单一
- `S-STR-02` 结构体方法数超过 10 个时必须拆分为多个结构体
- `S-STR-03` 禁止在同一结构体中混合数据获取、业务计算、持久化、通知四类职责中的任意两类
- `S-STR-04` 结构体不得同时持有数据库连接和 HTTP 客户端，二者属于不同职责

**函数级别**

- `S-FN-01` 函数只做一件事，函数名能用一个动词短语完整描述其行为
- `S-FN-02` 函数行数不超过 50 行，超过时拆分为子函数
- `S-FN-03` 函数参数不超过 5 个，超过时封装为配置结构体
- `S-FN-04` 函数禁止同时承担计算和 I/O 操作
- `S-FN-05` 函数圈复杂度不超过 10

**量化领域职责边界**

| 职责       | 允许的操作                     | 禁止混入的操作     |
| ---------- | ------------------------------ | ------------------ |
| 数据获取层 | 连接数据源、解析响应、格式转换 | 指标计算、策略判断 |
| 指标计算层 | 数学运算、序列处理             | 数据获取、信号输出 |
| 策略信号层 | 条件判断、信号生成             | 订单执行、持仓管理 |
| 风控检查层 | 风险度量、阈值判断             | 策略逻辑、通知发送 |
| 订单执行层 | 下单、撤单、查询               | 策略计算、风控判断 |
| 仓位管理层 | 持仓记录、盈亏计算             | 信号生成、通知发送 |
| 通知层     | 消息格式化、发送               | 任何业务逻辑       |

## O — 开闭原则 (Open/Closed Principle)

### 核心定义

> 模块对扩展开放，对修改关闭。新增功能通过实现接口扩展，不修改已有稳定代码

### 规则列表

**接口设计**

- `O-ITF-01` 所有可预见的变化点必须抽象为接口，不得使用具体类型作为扩展点
- `O-ITF-02` 接口定义在使用方包中，不得定义在实现方包中
- `O-ITF-03` 接口一旦发布，禁止修改已有方法签名，新增能力通过新接口扩展
- `O-ITF-04` 禁止使用类型断言 `.(ConcreteType)` 来判断并执行不同逻辑，必须通过接口多态实现

**策略扩展**

- `O-STG-01` 新增交易策略只需实现 `Strategy` 接口并注册，禁止修改策略调度器代码
- `O-STG-02` 新增技术指标只需添加新计算函数，禁止修改已有指标函数
- `O-STG-03` 新增信号过滤规则通过实现 `SignalFilter` 接口扩展，禁止在聚合器中添加 `if/switch` 分支

**执行扩展**

- `O-EXC-01` 新增交易所对接只需实现 `Exchange` 接口，禁止修改执行引擎核心代码
- `O-EXC-02` 新增订单类型通过策略模式扩展，禁止在执行器中使用 `switch orderType` 判断

**数据扩展**

- `O-DAT-01` 新增数据源只需实现 `DataReader` 接口，禁止修改策略层数据调用代码
- `O-DAT-02` 新增持久化方案只需实现 `Repository` 接口，禁止修改业务层存储调用代码

**风控扩展**

- `O-RSK-01` 新增风控规则通过实现 `RiskRule` 接口并注册，禁止修改风控引擎主流程
- `O-RSK-02` 风控规则之间禁止直接调用，通过风控引擎统一编排

**违规判断标准**

- 每次新增策略/数据源/交易所时，若需修改核心调度代码，则违反 OCP
- 业务代码中出现 `switch strategyType`、`if exchange == "binance"` 等枚举判断，则违反 OCP

## L — 里氏替换原则 (Liskov Substitution Principle)

### 核心定义

> 所有接口实现必须能无差别地替换其接口类型使用，不改变程序的正确性和预期行为

### 规则列表

**行为契约**

- `L-CTR-01` 接口实现方的方法前置条件不得强于接口定义的约定
- `L-CTR-02` 接口实现方的方法后置条件不得弱于接口定义的约定
- `L-CTR-03` 接口实现方不得抛出接口未声明的错误类型
- `L-CTR-04` 接口方法返回 `nil` 的条件必须与接口文档约定完全一致

**禁止行为**

- `L-FBD-01` 禁止接口实现方法中 `panic`，所有错误通过 `error` 返回
- `L-FBD-02` 禁止接口实现方法返回接口文档未约定的空集合或零值以表示特殊含义
- `L-FBD-03` 禁止 Mock 实现与生产实现在相同输入下产生结构差异迥异的输出
- `L-FBD-04` 禁止实现方在接口方法中修改调用方传入参数的内容

**Mock 实现规则**

- `L-MCK-01` Mock 实现必须通过与生产实现相同的接口测试套件验证
- `L-MCK-02` 回测用 Mock 交易所必须模拟真实交易所的所有错误场景（余额不足、最小数量限制等）
- `L-MCK-03` Mock 实现的方法执行耗时应可配置，不得默认为零延迟掩盖并发问题
- `L-MCK-04` Mock 实现必须实现接口的全部方法，禁止返回 `not implemented` 错误

**量化场景约束**

| 接口          | 替换场景                   | 必须保证的行为一致性                |
| ------------- | -------------------------- | ----------------------------------- |
| `Exchange`    | Binance ↔ OKX ↔ Mock       | 下单成功必须返回有效 OrderID        |
| `DataReader`  | DB ↔ CSV ↔ API ↔ Mock      | 相同参数返回相同数量的数据          |
| `Strategy`    | 任意策略互换               | 无信号时返回 nil，不返回零值 Signal |
| `RiskChecker` | 严格风控 ↔ 宽松风控 ↔ Mock | 通过风控必须返回 nil error          |
| `Notifier`    | Slack ↔ Email ↔ Log ↔ Mock | 发送失败不得影响主流程              |

## I — 接口隔离原则 (Interface Segregation Principle)

### 核心定义

> 调用方不应被迫依赖它不使用的方法，接口应按调用方需求最小化定义

### 规则列表

**接口粒度**

- `I-GRN-01` 接口方法数原则上不超过 5 个，超过时必须评审是否需要拆分
- `I-GRN-02` 接口按调用方角色定义，而非按实现方能力定义
- `I-GRN-03` 禁止将读操作和写操作定义在同一接口中，除非调用方同时需要两者
- `I-GRN-04` 禁止将订阅/流式接口与请求/响应接口合并

**量化领域接口划分**

```
数据域：
  CandleReader      → 读K线（策略层使用）
  CandleWriter      → 写K线（采集层使用）
  TickSubscriber    → 订阅Tick（高频策略使用）
  OrderBookReader   → 读盘口（做市策略使用）

执行域：
  OrderPlacer       → 下单（执行引擎使用）
  OrderCanceller    → 撤单（风控层使用）
  OrderQuerier      → 查询（对账服务使用）
  BalanceQuerier    → 余额查询（仓位管理使用）

策略域：
  SignalGenerator   → 生成信号（调度器使用）
  StrategyConfig    → 读取配置（管理后台使用）
  StrategyMetrics   → 输出指标（监控系统使用）

风控域：
  RiskChecker       → 风险检查（执行前使用）
  DrawdownMonitor   → 回撤监控（监控系统使用）
  PositionLimiter   → 仓位限制（下单前使用）
```

**依赖最小化规则**

- `I-DEP-01` 策略结构体只允许依赖 `CandleReader`，禁止依赖 `CandleWriter` 或完整 Repository
- `I-DEP-02` 执行引擎只允许依赖 `OrderPlacer`，禁止依赖完整 Exchange 接口
- `I-DEP-03` 回测引擎只允许依赖 `CandleReader`，禁止依赖实时数据订阅接口
- `I-DEP-04` 通知模块只允许依赖消息发送接口，禁止依赖任何业务域接口
- `I-DEP-05` 监控模块只允许依赖只读 Metrics 接口，禁止依赖任何写操作接口

**实现聚合规则**

- `I-AGG-01` 一个具体实现可以同时实现多个细粒度接口
- `I-AGG-02` 组合多个细粒度接口时，使用接口嵌套而非合并为新的大接口
- `I-AGG-03` 应用层装配时按需组合接口，不得向下层传递用不到的接口能力

**违规判断标准**

- 调用方使用接口时有方法从未调用，则违反 ISP
- 为实现接口而写出 `return nil, errors.New("not supported")` 的方法，则违反 ISP
- Mock 实现中有空方法体或 `panic("todo")`，则违反 ISP

## D — 依赖倒置原则 (Dependency Inversion Principle)

### 核心定义

> 高层业务模块不依赖低层实现模块，两者都依赖抽象接口；抽象定义在高层，实现细节依赖抽象

### 规则列表

**依赖方向**

- `D-DIR-01` 依赖关系只能从外层指向内层：`基础设施 → 应用层 → 领域层`，禁止反向依赖
- `D-DIR-02` 领域层禁止 `import` 任何基础设施包（数据库驱动、HTTP 客户端、消息队列等）
- `D-DIR-03` 策略层禁止 `import` 执行层，二者通过接口解耦
- `D-DIR-04` 禁止循环依赖，CI 必须集成循环依赖检测

**接口归属**

- `D-OWN-01` 接口必须定义在调用方（高层模块）所在包，不得定义在实现方包中
- `D-OWN-02` 交易所接口定义在执行引擎包，Binance 实现在基础设施包
- `D-OWN-03` 数据读取接口定义在策略包或应用包，数据库实现在基础设施包
- `D-OWN-04` 通知接口定义在应用包，Slack/Email 实现在基础设施包

**依赖注入**

- `D-INJ-01` 所有外部依赖通过构造函数参数注入，禁止在函数内部 `new` 具体实现
- `D-INJ-02` 禁止使用全局变量传递依赖，禁止使用 `init()` 初始化业务依赖
- `D-INJ-03` 构造函数参数类型必须为接口，禁止接受具体结构体指针（领域模型除外）
- `D-INJ-04` 测试环境与生产环境的区别只在装配层体现，业务代码零修改

**装配层规则**

- `D-WIR-01` 依赖装配集中在 `main.go` 或专用 `wire.go` 中，禁止在业务层散落装配逻辑
- `D-WIR-02` 生产装配和回测装配必须使用同一套业务核心代码，只替换基础设施实现
- `D-WIR-03` 推荐使用 `google/wire` 或显式手动装配，禁止使用反射型 DI 容器

**量化架构分层依赖规则**

```
允许的依赖方向（→ 表示可以依赖）：

main / wire
  → application（应用服务）
    → domain（领域模型）
    → [Strategy 接口]
    → [Exchange 接口]
    → [DataReader 接口]
    → [RiskChecker 接口]
    → [Notifier 接口]

infra/binance    → [Exchange 接口]
infra/postgres   → [Repository 接口]
infra/slack      → [Notifier 接口]
strategy/ma      → [Strategy 接口]
strategy/rsi     → [Strategy 接口]

禁止的依赖方向（✗）：

domain           ✗ → infra/*
domain           ✗ → strategy/*
strategy/*       ✗ → infra/*
strategy/*       ✗ → execution/*
application      ✗ → infra/*（只能依赖接口）
```

**配置与环境**

- `D-CFG-01` 配置结构体属于应用层，不得在基础设施层定义业务配置
- `D-CFG-02` 环境变量读取只在装配层进行，业务代码通过注入的配置结构体获取参数
- `D-CFG-03` 禁止在策略代码中直接读取环境变量或配置文件

## 综合强制规则

### 违规处理

- `RULE-ENF-01` SOLID 规则检查必须集成到 CI/CD 流程，违规阻断合并
- `RULE-ENF-02` 使用 `go vet`、`golangci-lint` 静态分析，配置接口实现验证
- `RULE-ENF-03` 每个接口必须有对应的契约测试，Mock 和生产实现都必须通过

### 评审检查清单

| 检查项                     | 通过标准                      |
| -------------------------- | ----------------------------- |
| 新增文件是否只有一个职责   | 文件名能单一词组描述其职责    |
| 新增功能是否修改了稳定模块 | Git diff 中核心调度代码无变化 |
| 新增接口实现是否可完全替换 | 替换后所有测试绿色通过        |
| 调用方依赖接口是否最小     | 接口中无未调用的方法          |
| 依赖方向是否符合分层规则   | `go mod graph` 无反向依赖     |

### 优先级说明

```
违反严重程度：DIP > ISP > OCP > LSP > SRP

DIP 违反 → 立即阻断，无法测试替换
ISP 违反 → 立即阻断，产生不必要耦合
OCP 违反 → 本次修复，下次扩展必须遵守
LSP 违反 → 本次修复，影响回测可信度
SRP 违反 → 计划重构，累积导致可维护性下降
```
