# 审查策略

> 每层轻审查，转换点强审查，高风险点反审查。

最后更新：2026-06-08

---

## 一句话原则

**审查**：确认"这一层是否正确承接上一层"。
**反审查**：刻意寻找"这一层哪里可能错、漏、偏、被误用、被模型误解"。

---

## 管线审查总览

```text
Spec ──审查──→ Matrix ──审查──→ Tasks ──审查──→ Plan ──审查──→ Prompt ──审查──→ Code
                                                                              │
                                                                              ↓
                                                            反向验收 ──→ Code → Spec
```text

每一层都做轻量审查；关键转换点做强审查；高风险内容做反向/对抗性审查。

---

## 各环节审查重点

| 环节 | 审查重点 | 反审查重点 |
|------|----------|------------|
| **Spec** | 需求是否清楚、边界是否明确、目标是否可验证 | 有没有隐藏假设？有没有歧义？有没有不该做的需求？ |
| **Matrix** | 是否把 Spec 拆成可追踪的能力、约束、验收标准 | 有没有遗漏需求？有没有伪需求？优先级是否被扭曲？ |
| **Tasks** | 每个任务是否对应 Matrix 项，粒度是否可执行 | 有没有任务做了但不产生价值？有没有关键任务没被拆出来？ |
| **Plan** | 顺序是否合理，依赖是否清楚，风险是否可控 | 有没有更简单路径？有没有先做错方向的风险？ |
| **Prompt** | Prompt 是否完整传递任务、约束、上下文和输出格式 | 模型会不会误解？有没有诱导幻觉？有没有缺少验收标准？ |
| **Code** | 是否满足任务、能运行、通过测试、可维护 | 有没有边界错误、安全问题、性能问题、不可见副作用？ |

---

## 最重要的三件事

### 1. 追踪性

每一层都要能回答：

> 这个东西从哪里来？对应上游哪一条需求？最终由哪段代码实现？

```text
Spec S1: 用户可以上传文件
Matrix M1: 文件上传能力
Task T1: 实现上传接口
Plan P1: 先做 API，再做前端
Prompt PR1: 让模型生成上传接口
Code C1: /api/upload
Test X1: 上传 pdf/png 成功，超大文件失败
```text

如果某个 Task、Prompt 或 Code 找不到上游来源 → **野生需求**
如果某个 Spec 找不到下游实现 → **遗漏需求**

### 2. 转换损耗

每次从一层转到下一层，都问：

> 有没有信息被丢掉？有没有新假设被偷偷加进去？

最容易出问题的转换：

```text
Spec → Matrix
Matrix → Tasks
Tasks/Plan → Prompt
Prompt → Code        ← 最危险，模型会"补全"你没说清楚的东西
```text

### 3. 反向验证

不要只从上往下看，也要从下往上看：

```text
Code → Prompt → Plan → Tasks → Matrix → Spec
```text

问：

> 这段代码真的服务于原始 Spec 吗？
> 有没有代码实现了一个看似合理、但并非用户真正要求的东西？

## 不同风险等级的审查强度

### 低风险（内部工具、Demo、一次性脚本）

```text
Spec 简查
Matrix 可省略或轻量
Tasks 简查
Plan 简查
Prompt 简查
Code 重点查
```text

### 中风险（业务功能、客户可见功能）

```text
Spec 审查
Matrix 审查
Tasks 审查
Plan 审查
Prompt 审查
Code 审查 + 测试
```text

### 高风险（支付、权限、隐私、金融、合规、安全）

```text
每一层都审查
关键层做反审查
Code 做安全审查、测试、回归、边界测试
Prompt 做注入/误解/越权检查
Matrix 做完整性和合规性检查
```text

**FoundationX 量化交易属于高风险**：涉及资金、订单、交易所接口的模块，每一层都必须审查，关键层做反审查。

## 每层最小检查清单

### Spec 审查

**正向：**

- 目标是什么？
- 不做什么？
- 用户是谁？
- 成功标准是什么？
- 失败场景是什么？
- 边界条件是什么？
- 约束是什么？

**反向：**

- 这个需求有没有歧义？
- 有没有互相冲突的要求？
- 有没有隐藏的安全、隐私、权限风险？
- 有没有不可验证的描述？

### Matrix 审查

**正向：**

- 每条 Spec 是否都有 Matrix 项？
- 每个 Matrix 项是否有验收标准？
- 是否标注优先级？
- 是否标注依赖和风险？

**反向：**

- 有没有"看起来合理但 Spec 没要求"的项？
- 有没有把一个需求拆错方向？
- 有没有遗漏非功能需求（性能、安全、兼容性）？

### Tasks 审查

**正向：**

- 任务是否足够小？
- 任务是否可完成？
- 任务是否可测试？
- 任务是否对应 Matrix？
- 任务之间依赖是否清楚？

**反向：**

- 有没有任务过大？
- 有没有任务无法验收？
- 有没有任务只是忙碌但不产生结果？
- 有没有关键路径被拆散导致风险变高？

### Plan 审查

**正向：**

- 顺序是否合理？
- 先做什么，后做什么？
- 是否先处理高风险部分？
- 是否有回滚方案？
- 是否有测试节点？

**反向：**

- 有没有更短路径？
- 有没有先实现低价值部分的问题？
- 有没有依赖没准备好？
- 有没有把不确定性留到最后？

### Prompt 审查

**正向：**

- Prompt 是否包含背景？
- 是否包含明确目标？
- 是否包含输入输出？
- 是否包含约束？
- 是否包含禁止项？
- 是否包含验收标准？
- 是否说明代码风格、框架、版本？

**反向：**

- 模型会不会误解？
- 模型是否会自行发明不存在的需求？
- Prompt 是否缺少边界情况？
- Prompt 是否会导致过度实现？
- Prompt 是否有注入风险或上下文污染？

**一个好的 Prompt 不只是"让模型写代码"，而是让模型知道：**

```text
写什么
为什么写
不要写什么
怎么算完成
如何验证
```text

### Code 审查

**正向：**

- 是否满足任务？
- 是否能运行？
- 是否通过测试？
- 是否处理异常？
- 是否可读？
- 是否可维护？
- 是否没有明显重复？
- 是否符合架构？

**反向：**

- 有没有安全漏洞？
- 有没有边界条件错误？
- 有没有权限绕过？
- 有没有数据泄露？
- 有没有竞态条件？
- 有没有隐藏副作用？
- 有没有性能问题？
- 有没有模型编造的 API 或不存在的库？

## 推荐流程

```text
1. Spec 审查                    ← spec-review agent
2. Spec → Matrix 转换审查        ← 轻量，人工或 task-split 自查
3. Matrix → Tasks 覆盖性审查     ← 轻量，人工确认
4. Tasks → Plan 可执行性审查     ← task-planner 输出后人工审批
5. Plan → Prompt 可传达性审查    ← prompt-builder 输出后人工确认
6. Prompt → Code 实现审查        ← task-executor 完成后 code-reviewer
7. Code → Spec 反向验收          ← 反向追溯，确认无野生需求
```text

**最重要的四个转换点：**

```text
Spec → Matrix        必须查
Matrix → Tasks       必须查
Prompt → Code        必须查
Code → Spec          必须查
```text

## 每层模板

给每一层都加这四个字段：

```text
来源：     上游追溯
目标：     本层要达成什么
验收标准：  怎么算完成
反审查问题： 可能错在哪里
```text

### 示例：Task 级别

```markdown
## TASK-003: 实现用户登录接口

### 来源
Matrix M2 - 用户认证能力

### 目标
支持用户通过邮箱和密码登录

### 验收标准
1. 正确账号密码返回 token
2. 错误密码返回 401
3. 空邮箱返回 400
4. 密码不泄露到日志

### 反审查问题
1. 是否会暴力破解？
2. 是否有错误信息泄露？
3. token 是否过期？
4. 是否遗漏 rate limit？
```text

---

## 总结

**不要只审查代码，要审查"需求如何一步步变成代码"。**

最小闭环：

```text
Spec 是否清楚
Matrix 是否完整
Tasks 是否可执行
Plan 是否合理
Prompt 是否不失真
Code 是否满足 Spec
```text
